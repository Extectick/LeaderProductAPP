# Сохранение офлайн-заказов: 24.09.2026

## Подтверждённая причина

На dev OTA 0.1.32.4 (APK 31, runtime 0.1.32) GlitchTip зарегистрировал
`NativeStatement.finalizeAsync` с причиной
`UNIQUE constraint failed: offline_drafts.user_id, offline_drafts.client_order_id`.
Это не недоступность 1С и не предыдущая ошибка блокировки SQLite.

При редактировании во время первого сохранения ответ правильно не затирал
свежий ввод, но UI-guid оставался пустым. Следующая запись искала черновик
только по этому guid и создавала второй локальный id с прежним clientOrderId.
Полная перезапись массива конфликтовала с уникальным ключом. Запись запускалась
дважды, одна Promise не ожидалась, ошибка снова запускала autosave через 400 мс.

Исходное воспроизведение: два элемента в памяти с одним clientOrderId;
транзакция второй записи откатывается, в SQLite остаётся только редакция 1.
Диагностика и воспроизведение: `.tmp/offline-save-diagnostic-20260924/repro.cjs`
в корне workspace. Контрольные события GlitchTip:
`d035ff46bc5347839e12ea05d2f117a3`, `9a3305629ab4492a85bed4ea5701e8fa`.

## Изменения APP

- Поиск локального документа использует clientOrderId, даже если UI-guid ещё нет.
- Вместо DELETE/INSERT всего списка — одна ожидаемая транзакция только изменённых
  документов и явно удаляемых редакций. Другие документы и пользователи не затронуты.
- SQLite разрешает повторный upsert с другим временным id по постоянному
  clientOrderId, не принимает устаревшую редакцию. Удаление после отправки имеет
  проверку clientRevision; строки удаляются явно в той же транзакции.
- UI сообщает об успехе и отправляет HTTP только после успешной локальной записи.
  При ошибке запись в памяти не подменяется якобы сохранённой версией.
- Нет повторяющихся autosave для той же ошибочной редакции. Новое редактирование
  или ручное сохранение разрешает повтор; технический текст не показывается пользователю.
- Ошибки чтения не выдаются за пустой список черновиков. Диагностика записи/чтения
  отправляется с ограничением частоты, без содержимого заказов.
- Старые дубликаты AsyncStorage объединяются по постоянному id с выбором последней
  редакции. Исходные данные удаляются только после успешной транзакции миграции.
- Возврат сети не отправляет заказы автоматически. Сохраняется ручная отправка в 1С.

## Проверки

- 86 тестов в 8 наборах: workspace, реальная SQLite, синхронизация справочников,
  ошибки, очередь записи, жизненный цикл SQLite и безопасное применение OTA.
- Регрессия: изменение количества во время первой записи, повторное сохранение —
  один id и следующая clientRevision, без отправки при восстановлении сети.
- Сбой/false локальной записи: нет сообщения об успехе, нет HTTP и бесконечных
  повторов; ручной повтор и новое редактирование успешно сохраняют документ.
- Реальный SQLite: независимые черновики, разделение пользователей, более новая
  редакция, запоздалое удаление, откат при ошибке строки и integrity_check=ok.
- Миграция дубликатов и сохранность AsyncStorage при её ошибке.
- `tsc --noEmit` и `git diff --check` — успешно.

На физическом телефоне проверка ещё требуется: применить OTA, выключить сеть,
создать заказ, несколько раз изменить/сохранить, перезапустить приложение и
убедиться, что сохранилась последняя редакция. Не очищать данные приложения.
