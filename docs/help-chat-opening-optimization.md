# Быстрое открытие переписки «Помощь»

Исследование начато 30 октября 2026. 31 октября реализованы начальный индекс FlashList, сокращённый путь восстановления измеренного якоря, анимация входа и удержание предыдущего экрана до готовности переписки. Доработки SQLite и сетевого пути из плана ниже пока не реализованы. Исправление анимации ответа ИИ — отдельное изменение.

## Устранение рывков при входе: дополнение 31 октября

Повторная диагностика обнаружила реальные коррекции уже показанного окна: ранний `onLoad` использовал ещё уточнявшиеся размеры; автоматическое удержание позиции FlashList конкурировало с восстановлением якоря; глобальный `focusKey` после ответа повторно фокусировал следующий composer. Android одновременно использовал оконный `adjustResize` и JS-компенсацию высоты. В стенде встречался также отчёт клавиатуры с высотой −24, который ошибочно убирал нижний safe area.

Исправлено:

- До первого показа начальная позиция имеет одного владельца. Автоматическое удержание FlashList отключено; проверяются реальные `isHeightMeasured` видимых элементов и совпадение геометрии/смещения на последовательных кадрах. Коммиты списка и изменения размеров возобновляют ограниченную проверку. Декодирования фотографий и сетевой тишины это не требует.
- Работавший до открытия ИИ и новые сообщения не блокируют появление чата до конца ответа: измеренный конец передаётся нативному follow. Анимация роста новых сообщений отключена только на время входа, после его окончания возвращается.
- Измеренная раскладка обычного текста хранится в ограниченном кэше текущего аккаунта (200 записей, ключ включает сообщение, текст, ширину окна и масштаб шрифта). Готовность изображений тоже переживает переключение список/чат внутри экрана «Помощь». Пиксели остаются в кэше Expo, React-деревья не сохраняются.
- Обычный вход очищает прежний запрос фокуса; создание обращения и явный ответ сохраняют свой запрос. Android полагается на `adjustResize`, iOS сохраняет `padding`. Нулевая/отрицательная высота клавиатуры не меняет safe area нижней панели.
- Переход использует аппаратный слой только во время своей анимации; после завершения он освобождается. Поздний callback от закрытого экрана не включает анимации следующего. Подход к ограничению слоя соответствует [рекомендациям React Native](https://reactnative.dev/docs/view#rendertohardwaretextureandroid).

Проверка на dev-эмуляторе API 36: четыре одинаковых повторных входа в три чата — сохранённые места с фото/ответами ИИ и конец переписки. Для 700 мс после сигнала показа сопоставлены часы Hermes `performance.now()` и нативный `SystemClock.uptimeMillis()`. Это проверка геометрии, не обещание частоты кадров на телефоне.

| Самопроизвольное изменение после разрешения показа | До, четыре входа | После, четыре входа |
|---|---|---|
| Диапазон нативного offset, dp | 14 / 284 / 46 / 553.5 | 0 / 0 / 0 / 0 |
| Изменение нижнего inset, dp | 24 / 24 / 24 / 24 | 0 / 0 / 0 / 0 |
| Максимальная добавочная анимация контента, dp | 0 / 0 / 28 / 0 | 0 / 0 / 0 / 0 |
| Незатребованный фокус ввода | во всех четырёх | ни в одном |

Все сохранённые message/sequence/offset совпали до и после. Запись переходов просмотрена; отдельно проверен повторный вход, пока локальный симулятор ИИ ещё имел статус `thinking`: чат готов через 437 мс, до завершения ответа. В дополнительном прогоне без записи разрешение показа занимало 576–680 мс; одновременно работал TypeScript, поэтому эти значения не используются как сравнительный benchmark. Release/profileable-сборка, физический телефон, iOS и холодное чтение SQLite в этом дополнении не профилировались.

Прошли 67 проверок timeline/пузырей/переходов и 5 дополнительных проверок фокуса, клавиатуры и начального режима нативной прокрутки; TypeScript также прошёл. Артефакты вне Git: `../.local-tools/ai-bubble-motion/entry-jank-before.json`, `entry-jank-final.json`, `entry-jank-report.json`, `entry-jank-final.mp4`, `entry-active-reopened2.json`. Более ранние замеры ниже относятся к предыдущим этапам реализации.

## Реализовано 31 октября

- Начальная цель передаётся в `initialScrollIndex` и `initialScrollIndexParams`. Для измеренного якоря/конца переписки позиция подтверждается в `onLoad`, без обязательного цикла повторной подготовки индекса. Остальные пути сохраняют коррекцию после измерения.
- Список обращений остаётся под входящей перепиской до окончания перехода. Его живой блюр при этом отключён, чтобы не обрабатывать два экрана одновременно. Вход: 150 мс, прозрачность и горизонтальное смещение 48 dp, native driver. Показ запускается после коммита позиционированного списка; состоянием показа владеет `HelpChatEntry`, поэтому он не требует повторного рендера `HelpScreen` и сообщений. При reduced motion переход мгновенный.
- Стрелка последних сообщений скрыта при открытии сохранённого места и при изменении раскладки/клавиатуры. Ручное движение вверх должно накопить 100 dp; движение вниз на 100 dp или достижение конца скрывает кнопку. Явный переход к найденному сообщению/дате допускает кнопку возврата. Появление/скрытие: 280 мс, scale 0.7 → 1, translateY 80 → 0 dp и прозрачность.
- Для дальнего перехода по дате прежний видимый фрагмент сначала монтируется отдельным слоем, пока оригинал остаётся на месте. Сервис заменяет окно только после готовности этого слоя. Входящий и уходящий слои имеют разные значения анимации: подготовка больше не уводит оригинал за экран. Касание отменяет ещё не начатый переход. Видимая дата не прокручивает и не выделяет сообщение; близкая использует обычную прокрутку.
- Загруженные фотографии сохраняют источник и состояние готовности в ограниченном хранилище экрана «Помощь» для текущего аккаунта (до 128 записей на resolver, без хранения пикселей в JS; отдельный timeline имеет локальный fallback). Копия для перелистывания использует только уже готовые оригиналы и не запускает собственную загрузку; повторное монтирование готового фото не включает лоадер и fade. Смена resolver/URL отделяет другой источник. Если нативный кэш был очищен, обычная ячейка один раз обновляет источник. В проверке альбома из шести фото число обращений к resolver до исправления росло с 6 до 12 при переходе по дате; после исправления осталось 6 при переходе и возврате. Переход проверен на записи Android; дополнительно прошли 43 целевые проверки изображений/даты и TypeScript.

Поведение входа сверено с [Telegram ActionBarLayout](https://github.com/DrKLO/Telegram/blob/master/TMessagesProj/src/main/java/org/telegram/ui/ActionBar/ActionBarLayout.java), порог стрелки — с [ChatActivity](https://github.com/DrKLO/Telegram/blob/master/TMessagesProj/src/main/java/org/telegram/ui/ChatActivity.java), её движение — с [ChatActivitySideControlsButtonsLayout](https://github.com/DrKLO/Telegram/blob/master/TMessagesProj/src/main/java/org/telegram/ui/Components/chat/layouts/ChatActivitySideControlsButtonsLayout.java). Это самостоятельная реализация на React Native Animated.

Сравнение 31 октября: тот же dev-эмулятор с программной графикой, один сохранённый чат из шести сообщений, якорь sequence=5, offset=12 dp. Это отдельный сценарий от исходного замера 30 октября ниже.

Медиана разрешения показа снизилась с 592 до 431 мс; дополнительные проходы позиционирования убраны, но первый рендер остаётся заметным. Записи входа, перехода по дате и ручной прокрутки проверены визуально; пустого экрана в проверенном дальнем переходе не наблюдалось.

## Что измерено

Dev Client, изолированный стенд `qa/help-preview`, Android API 36, эмулятор с программной графикой. Три повторных открытия одного сохранённого короткого чата: два сообщения и разделитель даты. Данные уже в памяти; API и SQLite в этом сценарии не участвуют. Запись экрана во время этих трёх замеров не велась.

Время от обработчика открытия, мс:

| Этап | Открытие 1 | Открытие 2 | Открытие 3 |
|---|---:|---:|---:|
| Данные подготовлены в памяти | 13 | 6 | 2 |
| FlashList сообщил `onLoad` | 537 | 648 | 616 |
| Переписка разрешена к показу | 1380 | 1394 | 1395 |

Само выполнение подготовки в fixture занимает 11 / 1 / 1 мс. После `onLoad` текст остаётся скрытым ещё 746–843 мс. Это время не является сетевой загрузкой. Метка завершения `await service.openTicket()` включает ожидание JS-продолжения и React-работу; её нельзя считать временем чтения данных.

Эти три измерения подтверждают механизм задержки, но не являются результатом для production или физического телефона и не позволяют вычислять P95. Время SQLite и REST на обычном клиенте пока не измерено.

## Причины в текущем коде

1. `HelpTimeline.tsx` монтируется заново при каждом входе (`key` содержит идентификатор обращения). Модели сообщений сохраняются, готовая раскладка списка — нет. Даже повторное открытие требует создания и измерения элементов.
2. Весь список имеет `opacity: 0`, пока `ready === false`. Начальное открытие внизу многократно вызывает прокрутку к концу и ждёт стабильной высоты последней строки: до восьми проходов `requestAnimationFrame`. При восстановлении якоря после `scrollToIndex` возможны до двенадцати проходов с двумя RAF на проход, до трёх стабильных смещений. Измеренный `latest`-сценарий уже задерживается; путь якоря требует отдельного замера.
3. Первый рендер занимает существенное время ещё до `onLoad`. На больших окнах к этому могут добавиться измерения строк вне видимой области: `drawDistance` сейчас минимум 1200 dp. В коротком измеренном чате всего два сообщения, поэтому увеличение окна не объясняет его задержку.
4. RAM и SQLite уже реализованы в `useHelpService.ts`. При попадании в RAM/SQLite обновление с сервера запускается в фоне. Добавление ещё одного кэша сообщений само по себе не исправит ожидание первого показа.
5. В дисковом пути есть дополнительная работа: сначала читается окно в конце, затем возможен повторный `readCachedHelpTicket()` около якоря. `readHistorySnapshot()` проходит через общую очередь эксклюзивных write-транзакций, хотя выполняет чтение. При занятой очереди это потенциальный источник задержки; в текущем стендовом замере он не участвует.
6. При сетевом промахе `openTicket()` ожидает сохранение страницы перед показом; для одного и того же окна возможны два `persistPage`. Этот путь тоже требует отдельного измерения.

Таймер 200 мс в `HelpTimeline` лишь откладывает появление лоадера при пустом списке. Он не задерживает показ готовых сообщений.

## Последовательность реализации

### 1. Начальная позиция и первый показ — первый приоритет

- Сформировать начальное окно и цель открытия до монтирования списка: последние сообщения, первое непрочитанное либо сохранённый якорь.
- Передавать начальный индекс и смещение в FlashList сразу (`initialScrollIndex` / `initialScrollIndexParams`), вместо первоначального рендера сверху с последующей серией прокруток.
- Для конца переписки подготовить отдельный путь начального размещения у нижнего края с учётом нативного inset поля ввода.
- Разрешать показ после первого корректно измеренного видимого окна и подтверждённого якоря. Повторные коррекции выполнять только при фактическом изменении геометрии; убрать обязательное ожидание нескольких одинаковых кадров для уже известной раскладки.
- Не просто удалять `opacity: 0`: это вернёт ранее наблюдавшиеся вспышки неправильной позиции и наложение сообщений.

### 2. Уменьшить работу первого рендера

- Кэшировать геометрию строк и видимое окно отдельно от данных. Ключ: учётная запись/API, message id и revision, ширина, масштаб шрифта, тема/стиль, группировка и геометрия вложений. Инвалидировать только изменившиеся строки.
- Сначала создавать видимый экран и небольшой запас; расширять запас после первого показа. Подобрать `drawDistance` по отдельному сценарию длинной переписки, сохранив отсутствие пустот при быстром скролле.
- Стабилизировать `renderMessage`, свойства строк и результаты группировки. Точечно измерить повторные рендеры, обработку аватарок, подписки на accessibility и поток dev-логов; менять их по результату измерений.
- При необходимости сохранять ограниченное число недавно открытых готовых окон, с вытеснением по памяти. Не держать React-деревья всех 30 записей RAM-кэша.
- Использовать уже существующую отложенную загрузку медиа. Текст и фиксированная геометрия фотографий должны быть готовы независимо от декодирования оригиналов.

### 3. Доработать чтение SQLite

- Получать ticket, read cursor, anchor и нужное окно одним согласованным чтением; выбирать окно около якоря внутри этой операции, без предварительного чтения ненужного хвоста.
- Вывести согласованные snapshot-чтения из очереди писателей через корректную read-транзакцию/соединение в WAL. Проверить согласованность record, ranges и messages при параллельной socket-записи; нельзя просто заменить транзакцию независимыми SELECT.
- Индекс `(scope, ticket_id, sequence)` уже есть. Не создавать дублирующий индекс.
- Текущее окно ограничено 100 сообщениями. Не увеличивать объём первого рендера вслепую ради ускорения открытия.

### 4. Убрать некритическую работу из пути показа

- На сетевом промахе показывать проверенное полученное окно без ожидания повторной записи того же snapshot.
- Оставить упорядоченное долговечное сохранение в фоне; sync cursor подтверждать только после успешного сохранения соответствующих событий.
- Outbox и правило сохранения собственного отправляемого сообщения до отправки не менять.
- REST/socket-сверка должна обновлять изменившиеся сообщения и строку обращения, сохраняя якорь и ссылки на неизменившиеся объекты. Повторно скрывать весь список не нужно.

### 5. Проверить именно открытие переписки

- Отдельные сценарии: повторное открытие из RAM, первый вход из SQLite после перезапуска, промах кэша/REST; для каждого — конец, сохранённое место чтения и непрочитанное сообщение.
- Короткая переписка, длинная история, чат с фотографиями, отсутствие сети. Проверить отсутствие старого чата/вспышек, стабильность якоря и сохранение пагинации.
- Сравнивать одинаковые сценарии и устройство. Контрольный замер — release/profileable-сборка на физическом Android; dev-эмулятор оставить для диагностики механизма.
- Предварительный целевой бюджет для повторного открытия из RAM на контрольном телефоне: обычно 150–200 мс до текста, P95 не более 250 мс. Это критерий приёмки для проверки после реализации, не обещание уже достигнутого результата. Для дискового открытия установить бюджет после его исходного замера.

## Диагностика

Добавлены события `chat.open.request`, `chat.open.cache`, `chat.open.data` (завершение вызова сервиса, включая ожидание JS-продолжения), `chat.open.listLoaded`, `chat.open.positioned`, `chat.open.visible`. Они работают только в dev и содержат идентификаторы/времена/количества без текста переписки, токенов и сетевых payload.

У обычного сервиса источник данных отмечается как `memory`, `sqlite` или `network`, у стенда — `fixture-memory`. Записи `visible` фиксируют React-коммит разрешения показа; точное время физического кадра при необходимости сверяется с записью экрана/Perfetto.

Локальные исходные артефакты текущего замера находятся вне Git: `../.local-tools/ai-bubble-motion/opening-events.json`. Для дальнейших узких прогонов доступен `node scripts/help-ui-diagnostics.mjs --port 8100`; он обращается напрямую к Hermes. Стенд следует подключать с достижимым адресом Metro, иначе приложение может продолжать показывать ранее загруженный JS.
