# Минималистичный запуск и обновления

## Поведение

- Холодный запуск и авторизация: только неподвижный логотип. APK проверяется в фоне и не удерживает заставку.
- Возврат в существующий экран через значок или список недавних приложений не создаёт заставку и не сбрасывает готовность React. Если Android действительно уничтожил процесс/Activity, это уже новый запуск, и заставка допустима.
- Реальная загрузка OTA на нативной заставке: «Обновляем», одна полоса и фактический процент. Если SDK ещё не сообщил прогресс, только на этой стадии полоса неопределённая, без выдуманного процента.
- Применение: «Запускаем», без полосы, второго индикатора и пояснений.
- Нет минимальной длительности заставки, технических подписей Runtime/OTA/APK и экранов с двойным лоадером.
- Debug, release и web используют один React-компонент `StartupLogoLoader`; старый импорт `StartupSplash` перенаправлен на него.

## Порядок запуска

1. Единственный launcher — `MainActivity` (`singleTask`). Старое имя `UpdateGateActivity` оставлено только как `activity-alias` для совместимости явных intents/ярлыков, без отдельной Activity и второй иконки. Deep links сохранены. Отдельный gate больше не запускает MainActivity поверх работающего приложения.
2. Штатный `ReactActivityDelegateWrapper`/`UpdatesPackage` ожидает выбор bundle вне UI-потока: `EX_UPDATES_CUSTOM_INIT=false`, `EX_UPDATES_ANDROID_DELAY_LOAD_APP=true`. `expo-updates` владеет StartupProcedure (`ON_LOAD`, Android metadata `ALWAYS`), rollback и React-событиями. Наш код не вызывает ручные initialize/start/check/fetch и не заменяет `eventManager.observer`.
3. Сетевое ожидание OTA ограничено `fallbackToCacheTimeout=8000`. Это максимум ожидания сети при доступной локальной версии, не минимальная длительность и не гарантия общего времени запуска. Ошибка или отсутствие новой версии завершают проверку раньше; подготовка локальной базы/React требует отдельного времени.
4. Медленное скачивание продолжает SDK в фоне. React не ждёт `isStartupProcedureRunning/isChecking/isDownloading` повторно. Верхняя полоска показывает скачивание/готовность; позднее завершение не вызывает автоматический перезапуск.
5. Уже готовое к применению обновление до входа может применяться один раз. Совпадение downloaded/running ID не вызывает повторного reload даже при устаревшем pending. Ожидание reload ограничено 8 секундами; изменения состояния не продлевают дедлайн.
6. Инициализация уведомлений не блокирует вход. Из React убрана зависимость готовности от APK-check и его дополнительный 12-секундный таймер. Проверка APK остаётся с сетевым таймаутом updateService; необязательное обновление показывается в баннере, обязательное — в модалке без возможности закрытия поверх смонтированного приложения. Ошибка проверки не прячет рабочий экран. Полоса APK не показывается на стадиях простой доступности/ошибки.
7. `LeaderStartupOverlay` создаётся только в `MainActivity.onCreate`, до `super.onCreate` регистрирует `CONTENT_APPEARED`, после — добавляет поверхность. При первом React-контенте/уничтожении Activity удаляет поверхность, подписку и coroutine. Из `onResume`/`onNewIntent` ничего не создаётся. Прогресс читается снимком SDK на IO-потоке раз в 250 мс только в STARTED; это не задержка запуска. Единственную событийную подписку Expo сохраняет у себя.
8. В MainActivity один `installSplashScreen`, выход без дополнительной fade-анимации. Config plugin убирает регистрацию `SplashScreenManager`, чтобы не было двух владельцев одной заставки. Поскольку MainActivity mods выполняются в обратном порядке, в `app.config.ts` наш plugin должен находиться **перед** `expo-splash-screen`; это проверяет тест с настоящим Expo mod. Повторный prebuild идемпотентен и не заменяет остальной lifecycle/обработку Back.

Источник поведения SDK: [Expo — How EAS Update works](https://docs.expo.dev/eas-update/how-it-works/).

## Защита окружения при локальной сборке

20.09.2026 проверка готового APK обнаружила локальный API в JavaScript при правильном dev URL в Android manifest. Такой APK не публиковался.

Причина: `@expo/cli` в `exportEmbedAsync` при `CI=1` отключает переданный Gradle флаг `--reset-cache`. Сохранённые трансформации Metro содержали уже подставленное значение `EXPO_PUBLIC_API_URL_DEV` из предыдущей локальной сборки. Повторная сборка с корректным окружением без смены ключа кэша воспроизводила проблему.

Исправление: `metro.config.js` добавляет в `cacheVersion` SHA-256 от отсортированных `EXPO_PUBLIC_*` и `NODE_ENV`. Кэш dev, local и prod разделён; приватные переменные в расчёт не входят. Четыре теста `metroEnvironmentCache.unit.test.ts` проверяют изоляцию, стабильность порядка и отсутствие влияния приватных значений.

Для локального dev release явно задавать API `https://dev.leader-product.ru`, канал `dev`, OTA URL этого же сервера и `NODE_ENV=production`. Публичные настройки ботов сохранять. `EXPO_NO_DOTENV=1` допустим после явного формирования окружения, но сам по себе не исправляет уже сохранённые трансформации. Перед публикацией проверять не только manifest, но и встроенный JavaScript, подпись, версию и checksum скачанного APK. При смене параметров упаковки явно перезапускать `app:createBundleReleaseJsAndAssets --rerun`; полный Gradle clean не нужен.
