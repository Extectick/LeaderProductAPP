# Загрузка офлайн-данных: очередь записи SQLite

Дата: 21.09.2026. Изменения только APP, без обновления API или 1С.

## Симптом и найденная причина

При нажатии «Загрузить данные на телефон» пользователь видел внутреннюю
ошибку `NativeStatement.finalizeAsync`. Полный native cause с устройства
недоступен, поэтому точную ошибку конкретного телефона ещё нужно подтвердить.

В коде обнаружены конкурирующие записи: три офлайн-набора скачиваются
параллельно, а каждый открывает отдельную exclusive-транзакцию Expo SQLite.
Параллельно могут сохраняться каталог, черновик и время синхронизации.
Exclusive-транзакция Expo не является очередью писателей. Тест на настоящем
SQLite воспроизводит `database is locked` при таком пересечении.
`runAsync` в установленном expo-sqlite вызывает finalize в finally, поэтому
ошибка освобождения statement может скрыть первоначальную ошибку выполнения.

## Дополнение 22.09.2026: native crash при закрытии FTS

В dev 0.1.32 / code 31 получен реальный fatal event
`f2caa93ed159423e6d1d963c40fcafcc` от 21.09.2026 11:51:17 UTC,
Android 16, экран `(main)/services/client_orders`. Стек:
`NativeDatabaseBinding::sqlite3_close → exsqlite3_finalize → abort`.
Это отдельный native дефект, не та же ошибка блокировки писателей.

Установленный expo-sqlite 57.0.1 по умолчанию перед close перебирает и
финализирует **все** statements. В этот список попадают внутренние statements
FTS5. При закрытии SQLite FTS освобождает их повторно. Механизм соответствует
[Expo issue #38168](https://github.com/expo/expo/issues/38168).
По стеку локализован путь сбоя; воспроизведение именно на устройстве пока не выполнено.

### Исправление

- В единственной точке открытия каталога выставлено
  `finalizeUnusedStatementsBeforeClosing: false`.
  `Transaction.createAsync()` установленной Expo-библиотеки копирует options
  исходного соединения, поэтому защита действует и на каждую exclusive-транзакцию.
- Явное освобождение app-owned statements оставлено: `withSQLiteStatements`
  и `finally` встроенных Expo-хелперов `runAsync/getFirstAsync/getAllAsync`.
  Отказ от blanket cleanup не является отказом от закрытия запросов приложения.
- После ошибки миграции соединение закрывается **до** сброса singleton и повторной
  попытки. При ошибке закрытия сохраняется первоначальная диагностическая ошибка.
- Файл базы, схема, данные, черновики и последовательная очередь писателей не удаляются
  и не заменяются. Изменение не затрагивает API/1С/нативные зависимости.

## 23.09.2026: применение OTA и счётчик элементов

В 0.1.32.3 получено событие `3498fa6aab8c4b49bdaf6713efc3fa93`
(11:54:36.257 UTC): `NativeStatement.finalizeAsync → database is locked`,
этап `offline.entity`, набор `agreements`. Время запуска процесса — 08:46:53 UTC,
то есть он пережил OTA. Пользователь подтвердил, что после полного перезапуска
загрузка завершилась. В соответствующем интервале dev API не возвращал ошибок
выгрузки; сбой произошёл при локальной записи.

Анализ установленного expo-sqlite выявил риск освобождения native handles при
JS reload: `removeAllCachedDatabases` очищает тот же mutable list, который
возвращает для закрытия. Это согласуется с пережившей перезапуск блокировкой,
но конкретная оставшаяся транзакция телефона не измерена. Нативная библиотека
в этой доработке не меняется.

### Безопасный OTA reload

- Обе точки `Updates.reloadAsync` используют общий single-flight barrier.
- Применение отложено, пока загружаются справочники, сохраняется заказ либо
  есть несохранённые изменения в открытом заказе.
- SQLite прекращает принимать новые операции, дожидается принятых чтений
  и всей очереди транзакций (включая native close), затем явно закрывает
  собственное соединение до вызова reload. Закрытый handle сбрасывается.
- Таймаут 8 секунд: запоздавшая подготовка не может перезапустить приложение.
  Ошибка/таймаут возвращает доступ к данным; база и черновики не удаляются.
- Если native close завершился ошибкой, повтор не считается успешным
  закрытием: предлагается полностью перезапустить приложение.
- При ошибке применения обновление остаётся доступным; исключение не уходит
  необработанным из обработчика нажатия. Телеметрия не задерживает reload.

### Уточнение интерфейса пользователем

Предыдущее отображение количества справочников заменено количеством элементов
текущего справочника. Слева по-прежнему «Загружаем/Обновляем цены» и т. п.;
справа, например, `7 000/7 879`. Фон отражает общий прогресс всех наборов.
Высота 34 dp, одна строка, счётчик не сжимается, длинное название сокращается.

В полной выгрузке знаменатель берётся из manifest; число загруженных строк
обновляется после сохранения страницы. При скачивании изменений API не
сообщает их итоговое количество заранее: показывается `N/…`, затем `N/N`
после последней страницы. Разница ревизий и общее количество строк таблицы
не выдаются за количество изменённых элементов. Неизменённый набор использует
фактическое сохранённое количество. При подготовке/финальном сохранении
счётчик скрыт, а не заменён прежним `11/12`.
